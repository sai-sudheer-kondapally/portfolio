Work That Shipped

Three deep examples from production environments. Real problems, real constraints, real outcomes — not theoretical best practices.

01
AWS WAF · Splunk · Terraform · Jolttek Inc · 2024–2025
Silencing WAF Noise Without Weakening Defense
The Problem
Rate-based WAF rules were blocking legitimate users during traffic spikes. Security team was spending 8+ hours per week triaging false positives manually. Engineering complained. Pressure to loosen rules was growing.
What I Built
A systematic tuning pipeline: deploy new rules in COUNT mode, baseline FP rate in Splunk using SPL queries segmented by user-agent / cookie / URI path, write precision exceptions for legitimate patterns, flip to BLOCK only after FP rate confirmed below 1%. Repeat monthly with Splunk-driven review.
How I Built It
Terraform for all rule deployment (no console changes). Splunk dashboards for WAF event analysis — custom SPL for FP/TP rate trending. ServiceNow integration auto-routing confirmed incidents. JA3/JA4 fingerprinting layered on for bot traffic that evaded IP-based rules.
✓
False positives down 30% → SOC triage workload cut 30% → engineers stopped filing WAF exceptions → security team regained credibility with product. WAF fully Terraform, peer-reviewed, zero console changes.
02
Firewall Manager · Terraform · Multi-Account · Jolttek Inc · 2024–2025
One Policy Change. 350+ Accounts Secured.
The Problem
Inconsistent WAF configurations across a sprawling multi-account AWS organization. Different teams maintained different rules with different coverage gaps. No central visibility, no enforcement mechanism, constant audit findings.
What I Built
AWS Firewall Manager policy backed entirely by Terraform modules. One policy definition, enforced automatically across every CloudFront distribution, ALB, and Route 53 resolver in every account. New accounts inherit WAF + Shield + Bot Control coverage on creation — no manual step required.
How I Built It
Terraform provider aliasing for multi-account workspace deployment. Firewall Manager security policies with auto-remediation enabled. IP sets, regex pattern sets, and rate-based rules stored as parameterized Terraform modules. Per-account configuration via variable overrides — same codebase, different risk profiles.
✓
350+ accounts under one WAF policy → manual config effort cut 50% → config drift eliminated → PCI-DSS and HIPAA audit findings resolved → security now enforced structurally, not by documentation.
03
Qualys VMDR · AWS SSM · Golden AMI · Infoswift Software · 2023–2024
Making Vulnerability Management Actually Close Loops
The Problem
Qualys was deployed but coverage was ~60% — new instances launched without agents, scans weren't prioritized by real risk, and findings sat unassigned. Patch Tuesday came and went with the same vulnerabilities showing up on the next scan.
What I Built
A closed-loop VM pipeline: Qualys Cloud Agent baked into the Golden AMI (every new EC2 pre-registered on launch), scan triggered by EventBridge on Patch Tuesday, findings scored by CVSS + EPSS via Python, CRITICAL findings trigger Golden AMI rebuild, HIGH+ findings auto-create ServiceNow tickets with SLA assigned by severity.
How I Built It
EC2 Image Builder + Packer for Golden AMI pipeline. Terraform for EventBridge rules and SSM Run Command targeting. Python script for Qualys API → CVSS/EPSS correlation and TEC prioritization scoring. ServiceNow REST API for ticket creation with owner auto-assignment from AWS resource tags.
✓
Agent coverage 60% → 98% → CRITICAL CVE SLA dropped to 24h → zero manual scheduling → remediation verified by automated rescan. VM went from compliance checkbox to closed-loop security operation.
04
ACTIVE THREAT RESPONSE · AWS WAF · Bot Control · Splunk · Jolttek Inc · 2024
Stopping a Distributed Credential Stuffing Attack in Real Time
The Situation
Authentication traffic spiked across multiple CloudFront distributions during peak hours. Login endpoints showing distributed request bursts across /24 CIDR blocks — classic credential stuffing signature. Existing WAF rate rules were logging but not blocking: thresholds were scoped too broadly and the risk of blocking real users was paralyzing the response. Attack was live and progressing.
What I Did
Pulled login endpoint traffic from Splunk — isolated anomaly clusters by user-agent, request frequency, and geographic spread. Confirmed credential stuffing: low-and-slow, rotating IPs, abnormal auth attempt density. Deployed WAF rate-based rules scoped to login URIs via scope-down statements, added Bot Control Targeted for automation fingerprinting, and layered temporary IP reputation blocking. Rules ran in COUNT mode for a 30-minute validation window; flipped to BLOCK once FP rate confirmed below 0.5%.
How It Ran
The full response — from detection to active blocking — ran inside one hour. Terraform applied the rules; auto-rollback was configured if FP rate crossed threshold. ServiceNow incident was opened automatically as the attack was detected. After containment: the mitigation pattern was codified into a reusable Terraform WAF module and pushed via Firewall Manager to all 350+ accounts. A post-incident runbook was added to SOC documentation.
✓
Attack traffic reduced 90%+ within minutes of rule activation · zero legitimate user sessions blocked · detection + mitigation pattern deployed organization-wide · SOC runbook created for future recurrence · full audit trail in ServiceNow

How I Approach Problems

Senior security engineering is mostly a series of trade-offs. Here's how I navigate the ones that come up constantly.

RISK ↔ USABILITY
I default to neither blocking everything nor allowing everything
Locking everything down is easy. Blocking nothing is also easy. The hard work is building rules that catch actual attacks without impacting legitimate users. My approach: start every new rule in COUNT mode, measure real traffic patterns against a Splunk baseline, tune to below 1% false positive rate before switching to BLOCK. Security that breaks the product gets turned off. I'd rather have calibrated protection in place than perfect protection that nobody uses.
AUTOMATION ↔ HUMAN JUDGMENT
I automate the repeatable and protect the judgment calls
I automate: patch schedules, rule deployment, scan triggers, ticket creation, agent provisioning, compliance reporting. I keep humans in the loop for: exception approvals, FP suppression decisions, time-boxed waivers, and post-incident rule changes. Automation removes toil and enforces consistency. It doesn't replace accountability. Every automated action I build has an audit trail and a human who owns the policy behind it.
PREVENTION ↔ DETECTION
I design in layers because no single control is sufficient
WAF stops known attack signatures. JA3/JA4 fingerprinting catches sophisticated bots that WAF misses. GuardDuty sees lateral movement that happened after perimeter. Qualys finds what's exploitable before attackers do. Splunk correlates what all of them missed individually. I design security in depth not because it's best practice — but because I've seen what slips through any single layer. The goal is resilience, not the illusion of invulnerability.
